    01

    Python Classes & OOP

    Classes, objects, attributes, methods, constructors, encapsulation, and object state.

    What to know

    • A class is a blueprint; an object (instance) is one thing built from it. __init__ is the constructor and sets the starting state.
    • self is the instance. Instance attributes (self.x) belong to one object. Class attributes, written in the class body, are shared by every instance.
    • Methods are functions defined in the class that read or change the object's state.
    • Encapsulation is by convention: _name means internal, __name triggers name mangling. @property exposes a value read-only or validates it on assignment.
    • @classmethod receives the class as cls and is used for alternate constructors. @staticmethod receives neither the class nor the instance.
    • __repr__ returns a developer-friendly string. It's what pytest shows in failure output.

    Watch out for

    • Mutable default arguments. def __init__(self, presets=[]) shares one list across every instance. Use presets=None and create the list inside.
    • A list or dict in the class body (presets = []) is also shared. Per-object state belongs in __init__.
    • Forgetting self as the first parameter gives TypeError: ... takes 0 positional arguments but 1 was given.
    • A property and its stored attribute need different names (frequency and _frequency). Otherwise the setter calls itself until RecursionError.

    Inheritance & Polymorphism

    Base and derived classes, method overriding, super(), and a shared interface with different implementations.

    What to know

    • A derived class (class BluetoothAudio(MediaSource)) inherits every attribute and method of its base class.
    • Overriding means defining a method with the same name in the subclass. The subclass version is used.
    • super() calls the parent's version. In a subclass constructor, call super().__init__(...) so the parent's setup runs.
    • Polymorphism: code that calls source.play() works with any subclass, and each one behaves its own way. The caller never checks the type.
    • Abstract base classes (ABC with @abstractmethod) define a required interface. A class that leaves an abstract method unimplemented can't be instantiated.
    • isinstance(obj, Base) is True for subclasses too. Method lookup follows the MRO (BluetoothAudio.__mro__).

    Watch out for

    • Defining __init__ in a subclass replaces the parent's. Without super().__init__() the parent's attributes are never set, and you get AttributeError later.
    • Overriding a method with a different signature (an extra required argument) breaks callers that treat the object as the base type.
    • type(x) == MediaSource is False for subclasses. Use isinstance when you mean "is a kind of".

    SOLID Principles

    Recognize SRP, OCP, LSP, ISP and DIP and apply them in small framework refactoring examples.

    SSingle Responsibility

    A class should have one reason to change.

    SmellHeadUnitTester connects to the CAN bus, runs the test steps and writes the HTML report.

    FixSplit into CanClient, TestSteps and ReportWriter.

    OOpen/Closed

    Open for extension, closed for modification.

    SmellAn if source == "usb": ... elif source == "bt": ... chain you edit every time a source is added.

    FixA MediaSource base class. Adding CarPlay means a new CarPlayAudio subclass, no edits to existing code.

    LLiskov Substitution

    A subclass must work anywhere its base class works.

    SmellReadOnlyPresets(Presets) overrides save() to raise NotImplementedError.

    FixDon't inherit. Use separate readable and writable interfaces.

    IInterface Segregation

    Don't force a class to implement methods it doesn't use.

    SmellA VehicleModule interface with play_audio(), set_temperature() and navigate_to(). The HVAC class stubs out two of them.

    FixSmall interfaces: AudioOutput, ClimateControl, Navigator.

    DDependency Inversion

    Depend on abstractions, not concrete classes.

    SmellHvacController.__init__ creates PeakCanBus("PCAN_USBBUS1") itself, so every test needs real hardware.

    FixAccept a Bus in the constructor. Production passes a real bus; tests pass a Mock.

    In refactoring questions, name the principle and say what changes: "split X into Y and Z", "add a subclass instead of another elif", "inject the bus through the constructor". DIP is also what makes mocking easy in topic 6.

    04

    Pytest Basics

    Test discovery, assertions, exception testing, running tests, and interpreting failures.

    What to know

    • Discovery: files named test_*.py or *_test.py, functions starting with test_, and classes starting with Test that have no __init__.
    • Use a plain assert. Pytest rewrites it so a failure shows both sides of the comparison.
    • pytest.raises(ValueError, match="...") checks that code raises. match is a regular expression searched in the error message.
    • pytest.approx compares floats. 0.1 + 0.2 == 0.3 is False in Python.
    • Result letters: . passed, F failed (an assertion or exception in the test body), E error (an exception in a fixture's setup or teardown), s skipped, x expected failure.

    Reading a failure

    The > marks the failing line. E lines show the actual value on the left and the expected value on the right. The last block gives the file, line and the test's node ID, which you can pass straight back to pytest to rerun just that test.

    05

    Fixtures

    Reusable setup and cleanup with @pytest.fixture, including isolated test objects and dependencies.

    What to know

    • A fixture is a function decorated with @pytest.fixture. A test gets it by naming it as a parameter. You never call it yourself.
    • Code before yield is setup. Code after yield is teardown and runs even if the test fails.
    • Scope controls how often it's created: function (default, a fresh one per test), class, module, package, session.
    • Fixtures in conftest.py are available to every test in that folder and below, with no import.
    • Fixtures can request other fixtures. autouse=True applies a fixture to every test in its scope.
    • Built-ins worth knowing: tmp_path (a temporary directory), monkeypatch (set attributes or env vars, undone after the test), capsys (capture printed output).

    Watch out for

    • If setup raises before yield, the teardown doesn't run and the test is reported as E.
    • A broader-scoped fixture can't request a narrower one. A session fixture that asks for a function fixture fails with ScopeMismatch.
    • Sharing a mutable object through a module or session fixture breaks isolation: one test's changes leak into the next. Keep function scope for objects that tests modify.
    • Calling a fixture directly (tuner()) raises an error. Request it as a parameter.
    06

    Mocking with unittest.mock

    Mock, MagicMock, patch, side_effect, and verifying calls when hardware or services are unavailable.

    What to know

    • Mock() records every call made to it and returns a new Mock for any attribute you touch.
    • MagicMock() also supports magic methods such as len(), iteration and with. patch creates MagicMocks by default.
    • return_value sets what a call returns. side_effect can be an exception (raised), an iterable (one item per call) or a function (called with the same arguments).
    • Verify with assert_called_once_with(...), assert_called_with(...) (checks only the last call), assert_any_call(...), assert_not_called(), call_count and call_args_list.
    • patch("module.name") replaces a name for the duration of a test. Patch where the name is looked up, not where it was defined.
    • spec=RealClass or autospec=True makes the mock reject attributes and call signatures the real object doesn't have.

    Watch out for

    • Patching ivi.hw.scan_devices has no effect on a module that already ran from ivi.hw import scan_devices. That module holds its own reference, so patch ivi.bluetooth.scan_devices.
    • Without spec, a mock accepts typos such as bus.sned(...) and the test passes for the wrong reason.
    • An iterable side_effect raises StopIteration once it runs out of items.
    • assert_called_with checks only the most recent call. Use assert_any_call or call_args_list to check earlier ones.
    07

    Parametrized Tests

    Run one test with multiple datasets using @pytest.mark.parametrize, including valid and invalid transitions.

    What to know

    • @pytest.mark.parametrize("freq", [87.5, 99.9]) runs the test once per value. Each run is reported separately, for example test_valid_frequency[99.9].
    • For several arguments, pass a comma-separated name string and a list of tuples: "start, action, expected".
    • ids=[...] or pytest.param(..., id="...") gives readable case names. pytest.param(..., marks=pytest.mark.xfail) marks one case.
    • Stacking two parametrize decorators runs every combination.
    • Parametrized arguments and fixtures mix freely; both are just test parameters.
    • For a state machine, write one test for valid transitions and another for invalid ones that expects an exception.
    08

    Type Hints + mypy

    Annotate parameters and return values; identify incompatible arguments, returns, and undefined names.

    What to know

    • Annotate parameters and returns: def tune(self, freq: float) -> None:. Variables too: presets: dict[int, float] = {}.
    • Common types: int, str, list[str], dict[str, int], tuple[int, ...], str | None (same as Optional[str]), Callable[[int], bool], Any.
    • Hints aren't enforced at runtime. Python runs the code regardless; mypy is the tool that checks.
    • mypy reports incompatible arguments, incompatible return values, undefined names, and attribute access on a value that might be None.
    • Inside if dev is not None: mypy narrows the type, so the error goes away.
    • By default mypy skips the body of a function with no annotations at all. --strict enables the extra checks, including requiring annotations.

    Watch out for

    • A function with no annotations at all, like def reset(self):, is treated as untyped and mypy doesn't check inside it. Adding -> None makes it checked.
    • list[int] in lowercase needs Python 3.9+, and int | None needs 3.10+ (or from __future__ import annotations).
    • Each mypy line reads file:line: error: message [code]. The bracketed code tells you the kind of problem.
    09

    Ruff + PEP 8

    Naming, spacing, imports, line length, linting commands, auto-fix, and project configuration.

    What to know

    • Naming: snake_case for functions, variables and modules; PascalCase for classes; UPPER_CASE for constants; a leading underscore for internals.
    • Layout: 4-space indents. PEP 8 says 79 characters per line; Ruff defaults to 88. Two blank lines around top-level functions and classes, one between methods.
    • Imports at the top of the file, one per line, grouped as standard library, then third-party, then local. No from x import *.
    • Compare with None using is / is not. Put spaces around operators and after commas.
    • Ruff is both a linter and a formatter. ruff check reports rule violations; ruff format rewrites layout, Black-style.
    • Rule codes: E/W pycodestyle, F Pyflakes (F401 unused import, F841 unused variable, F821 undefined name), I import sorting, N naming, B bugbear, UP pyupgrade. The default selection is E4, E7, E9 and F.

    Watch out for

    • ruff check --fix applies only safe fixes. Others need --unsafe-fixes, and some (like naming) are never automatic.
    • E501 (line too long) isn't in the default rule set. Select E or E501 to turn it on.
    • # noqa: F401 silences one rule on one line. A bare # noqa silences every rule on that line, so prefer the specific code.
    • Lint settings belong under [tool.ruff.lint]. Putting select directly under [tool.ruff] is the older, deprecated form.
    10

    BDD / Gherkin / Behave

    Feature files, scenarios, Given/When/Then, step definitions, and Behave's execution flow.

    What to know

    • BDD describes behavior in plain language the whole team can read. Gherkin is the syntax; Behave is the Python runner.
    • A .feature file has one Feature, an optional Background (steps run before every scenario), then Scenarios built from Given (starting state), When (action) and Then (expected outcome). And and But take the type of the step before them.
    • Scenario Outline with an Examples table runs once per row, filling in the <placeholders>.
    • Step definitions are Python functions decorated with @given, @when or @then. {name} captures text, {n:d} converts to int, {x:f} to float.
    • context is passed to every step and hook. Store state on it (context.ivi = ...) to share it between steps.
    • Folder layout: features/*.feature, features/steps/*.py, and features/environment.py for hooks.

    Execution flow

    1. 1before_all(context) once per run
    2. 2before_feature(context, feature) per feature file
    3. 3before_scenario(context, scenario) per scenario, and per Examples row
    4. 4Background steps, then the scenario's steps each wrapped in before_step / after_step
    5. 5after_scenario(context, scenario) runs even when a step failed
    6. 6after_feature(context, feature)
    7. 7after_all(context)

    When a step fails, the remaining steps in that scenario are skipped and Behave moves on to the next scenario.

    Watch out for

    • Step text must match exactly, including quotes and punctuation. A mismatch shows as an undefined step; behave --dry-run lists them with ready-to-paste snippets.
    • The keyword type matters. A step defined with @given won't match when it's written as And ... after a When, because that And counts as a When. Use @step for text used in several positions.
    • Two definitions that match the same text cause an AmbiguousStep error.
    • Attributes set on context during a scenario are removed when it ends. Put things that must last the whole run on context in before_all.
